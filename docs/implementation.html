00

The premise & the decision

Rwanda's government websites run on TYPO3. The pain is not that TYPO3 is bad technology — it is that few local engineers know it, its community is small, and architectural knowledge lives in a handful of heads. That is a talent + ecosystem + governance problem wearing a technology costume.

The strategic decision has been made deliberately: we build our own platform rather than adopt or extend an existing one (Drupal/GovCMS, Payload, Directus, Strapi). The reason is sovereignty and institutional ownership — "we would rather fight with what we built." That is a legitimate stance taken by national platforms before us (e.g. GOV.UK).

Risk

A bespoke build risks reproducing the TYPO3 trap — a niche system only our team understands. The plan below is engineered specifically against that. The guardrails in §01 are non-negotiable, not aspirational.

01

Non-negotiables

Four commitments, baked in from the first commit. The first three keep the platform alive beyond the people who built it; the fourth keeps it lawful and consistent with national standards.

Non-negotiable 01

Boring, conventional tech

Every choice optimizes for hireability. NestJS, React, Next.js, Postgres — technologies a new engineer can already know and an AI assistant can already help with.

Non-negotiable 02

Open source from day one

A community cannot be retrofitted. Public repo, public docs, public roadmap — so knowledge and contributors can exist beyond the core team.

Non-negotiable 03

Plugin architecture

The core stays small and stable; features live at the edges. First-party features are built as plugins against the same public contract an outsider would use.

Non-negotiable 04

Conform to the RISA Websites Guideline

Every site the platform produces must satisfy the Government of Rwanda Websites Guideline — branding, accessibility, mandatory pages, security, SEO and portal integration. Conformance is enforced by the design system and delivery layer, not left to editors.

Guideline conformance — how each mandate is met

The RISA guideline is technology-agnostic except for one clause. We satisfy every requirement structurally — the platform makes a non-conforming site hard to produce.

Assets

Official national symbols — Coat of Arms, Government Logo, National Flag, National Anthem — are fetched from the canonical source at gov.rw/government/publications/national-symbols. Their characteristics and usage are determined by law, so the design system treats them as fixed, versioned assets — bundled with provenance, never re-drawn or recoloured by editors.

Dependency

The guideline currently names TYPO3 as the mandated CMS and references "TYPO3's built-in security." govcms replaces TYPO3, so platform adoption requires RISA to revise that single clause. This is a governance step, not an engineering one — treat it as an explicit project dependency, pursued in parallel with the pilot as proof.

What makes it a government CMS

  • Accessibility (WCAG 2.2 AA) enforced — can't publish inaccessible pages
  • Multi-tenancy at national scale, central patching
  • A government delivery design system = the national web identity (distinct from the CMS's own product UI — see below)
  • Multilingual as a core data concept (rw / en / fr / sw)
  • Workflow, approvals, immutable audit trail, records retention
  • Data sovereignty — runs on local/government infrastructure

What is deliberately commodity

The generic "CMS engine on a modern stack" is not the moat — modern headless CMSes already exist. Our value is the government layer above. We keep the engine small and conventional so effort concentrates where governments actually differ.

Two design systems, two rulebooks

The RISA guideline governs the output (citizen-facing sites), not the tool (the CMS itself). So govcms has two distinct design systems that share low-level primitives (shadcn/ui, Tailwind) but diverge entirely at the token and component level.

packages/admin-ui

Product design system

The CMS interface used by editors, reviewers and admins (apps/admin). govcms's own brand — a modern, productive SaaS feel. Free to diverge from gov guidelines; optimized for clarity and speed. A delightful editor is itself an adoption lever against TYPO3.

packages/design-system

Government delivery system

The national identity rendered on public sites (apps/site) — Coat of Arms, official palette, imigongo. RISA guideline is binding; conformance (AA contrast, mandatory alt text, approved palette only) is enforced structurally, not left to editors.

04

Hybrid tenancy model

The trick that makes hybrid work without two systems: the core is always tenant-aware, and "dedicated" is just where it runs. Every query carries a tenant_id; Postgres row-level security enforces isolation. A shared deployment holds many tenants in one database; a dedicated deployment holds exactly one. Same image, same migrations — different infrastructure. We never fork the code, so the whole fleet stays patchable.

Key

Because delivery is SSG/ISR, the CMS never serves citizen traffic. A defense site's dedicated instance and a district site's shared tenant both emit the same static output to a CDN. A traffic spike can't take down the editor, and the public attack surface is nearly zero.

05

Data model

The minimum that's actually right. Two deliberate decisions noted below.

Tenant         id, name, locales[], theme, deployment_mode
User           id, email, name
Membership     user_id, tenant_id, role           ← RBAC is per-tenant
ContentType    id, tenant_id, key, schema(JSON)    ← admin-defined fields
Entry          id, tenant_id, content_type_id, status, locale, slug
EntryVersion   entry_id, data(JSON), author_id, created_at   ← immutable
WorkflowState  entry_id, state, actor, ts          ← draft|review|approved|published
Media          id, tenant_id, path, alt_text(per-locale), meta
AuditLog       id, tenant_id, actor, action, target, before/after, ts

Versions are immutable

Edits write new EntryVersion rows; publishing points an entry at a version. Free rollback and a real audit trail — which government accountability requires.

Field schema is data

ContentType.schema (JSON, validated by the API) lets a non-developer define a "Tender" or "Public Service" type through the UI — no deploy. This is the flexibility we're paying for.

06

Repository structure

A standard pnpm + Turborepo monorepo. Note the two separate design-system packages (see §03).

govcms/
├── apps/
│   ├── core/          NestJS — API, RBAC, workflow, plugin host
│   ├── admin/         React + Vite — the CMS editor (uses admin-ui)
│   └── site/          Next.js — public SSG/ISR delivery (uses design-system)
├── packages/
│   ├── admin-ui/      product design system — govcms's own brand (apps/admin)
│   ├── design-system/ government delivery system — RISA-conformant (apps/site)
│   ├── content-sdk/   typed client the site uses to fetch content
│   ├── schema/        shared types + zod validators
│   └── plugin-api/    the contract plugins implement
└── plugins/           first-party plugins live here, like everyone else's
Why

First-party features go in plugins/ against the same plugin-api an outsider would use. That forces the extension contract to be real — the best defense against the "only we understand it" trap.

07

MVP scope — one pilot ministry, end to end

The MVP is not the platform. It's a thin vertical slice that proves the spine works.

In scope

  • Core API: tenancy + auth + 3 hardcoded content types (Page, News, Service)
  • Admin: login, create/edit/translate an entry, draft → review → publish, media upload with alt text
  • Site: Next.js build rendering those types as static pages, 2 locales (en + rw), design system applied
  • One real ministry's content migrated in, on a real domain

Deferred

  • User-defined content types (schema engine)
  • Full plugin host
  • Dedicated-instance deployment
  • Search
  • The remaining two languages (fr, sw)

Designed-for now, built after the pilot proves out.
